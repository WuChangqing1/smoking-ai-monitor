  （`/etc/nginx/conf.d/smoking-monitor.conf`，完全独立，不依赖其它站点）
- **备用入口**：`http://110.42.236.65/smoking/`

### 2.3 前端数据流（核心架构）

```
MonitorVideo（播放视频）
   │ register(<video>)
   ▼
VideoSyncProvider  ← 全站唯一时间源
   │ requestAnimationFrame 读取 video.currentTime
   │ resolveVideoTelemetry(t)          ← 唯一遥测解算点
   │ resolveDetectionBoxForRisk(risk)  ← 唯一检测框解算点
   │ buildCurrentAlarm(telemetry)      ← 唯一当前报警派生点
   ▼
VideoSyncContext
   ├──→ 综合监控（4 状态卡 / 趋势图 / 雷视摘要）
   ├──→ 雷视联动（雷达 + 视觉 + 联合判定 + 双趋势）
   ├──→ 异常报警（当前报警列表 + 侧栏角标）
   ├──→ 智能预警（buildSyncedPrediction 派生）
   └──→ 视频监控（四路机位）
```

**架构价值**：首页与雷视联动消费的是**同一个对象**，
因此不可能出现页面间数据不一致；侧栏角标与当前报警列表同源，同样不可能矛盾。

### 2.4 两种运行模式

由环境变量 `SMOKING_RUN_MODE` 选择，默认 `video_sync`。

| 模式 | 用途 | 数据来源 |
|---|---|---|
| **`video_sync`（默认）** | 正式展示 | 页面数值随主监控视频 `currentTime` 同步解算 |
| `automatic` | 开发 / 测试 / 逻辑验证 | 后端 `SimulationEngine` 自动工况循环 |

两种模式共用同一套业务状态规则（阈值、等级映射、联合判定口径）。
`SimulationEngine` 与 `automatic` 模式完整保留，未删除、未废弃；
`video_sync` 模式下只是关闭了它的事件登记开关（见轮次 9），
引擎本身仍在后台按 10 Hz 正常演化。

## 3. 数据模型与关键参数

### 3.1 状态机

```
normal（正常） → attention（关注） → warning（预警） → alarm（异常）
                                          ↑
                                    stopped（已停止，检测任务暂停）
```

- 状态机驱动：`severity` 0~1 是唯一自变量，**所有信号由它派生**
- 信号构成 = 趋势 + 漂移 + 带限振动 + 高斯噪声 + EMA 平滑
  → 不是直线，也不会出现多厘米级跳变
- 自动模式的驻留时间：正常 180 s / 关注 60 s / 预警 45 s / 异常 40 s
- 进入概率：`PROB_ENTER_WARNING = 0.32`、`PROB_ENTER_ALARM = 0.14`
- 恢复驻留：50 s
- 随机种子固定 `20250519` → 数据可复现，测试不会偶发失败

### 3.2 关键常量

| 常量 | 值 | 含义 |
|---|---|---|
| `BASELINE_DISTANCE` | 0.72 m | 主监控点基准距离 |
| `ALARM_THRESHOLD` | 0.58 m | 报警阈值 |
| `CONVEYOR_BASE_SPEED` | 1.20 m/s | 输送基准速度 |
| `TEMP_BASE` | 23.6 ℃ | 环境温度基准 |
| `HUMIDITY_BASE` | 54.0 % | 环境湿度基准 |
| `SAMPLE_RATE_HZ` | 10 | 采集频率 |
| `RADAR_MAX_REFRESH_HZ` | 1000 | 雷达最高刷新能力（设备规格） |
| `RISK_FLOOR` | 6.0 | 风险指数下限 |
| `RISK_WEIGHT_SEVERITY` | 88.0 | severity → 风险的权重 |
| `COVERAGE_BASE` / `COVERAGE_SPAN` | 0.18 / 0.68 | 覆盖率映射 |
| `CONVEYOR_SPEED_MAX_DROP` | 0.12 | 堵料时速度最大降幅 |
| 设备负载 | `48.0 + 38.0 × severity` | |
| `FORECAST_CEILING` | 96.0 % | 预测封顶，避免顶到 100% 的确定性结论 |
| 原始数据缓冲 | `deque(maxlen=6000)` | 10 分钟 |
| 报警记录缓冲 | `deque(maxlen=300)` | |

### 3.3 风险等级映射

| 风险指数 | 等级 | 文案 | 状态 | 检测框 |
|---|---|---|---|---|
| < 30 | `low` | 低风险 | 正常 | 无 |
| 30 ~ 55 | `medium` | 中风险 | 关注 | 无 |
| 55 ~ 80 | `high` | 高风险 | 预警 | **橙色框** |
| ≥ 80 | `critical` | 严重风险 | 异常 | **红色框** |

判定结论 → 报警等级：正常/关注 → `info`，预警 → `warning`，异常 → `critical`。

### 3.4 视频同步关键帧

源视频 0~10 s 轴上的遥测轨迹（前端与后端各有一份等价实现）：

| t (s) | 测距 (m) | 风险 (%) | 覆盖率 | 速度比 |
|---|---|---|---|---|
| 0 | 0.721 | 18 | 0.30 | 1.00 |
| 2 | 0.706 | 27 | 0.37 | 0.98 |
| 4 | 0.681 | 43 | 0.49 | 0.95 |
| 6 | 0.651 | 59 | 0.61 | 0.91 |
| 8 | 0.612 | 76 | 0.74 | 0.86 |
| 10 | 0.582 | 89 | 0.83 | 0.80 |

- **线性插值**，无分段跳变（`3.99s=0.70` → `4.00s=0.65` 这类情况不会出现）
- 叠加**确定性 sin 微扰**（±1~3 mm），同一个 `t` 结果永远一致，不使用随机数
- 终点收敛到 **0.582 m**，对应资料中的真实报警测量值 0.58 m

## 5. 功能模块详解

### 5.1 综合监控（首页）

## 6. 两个技术重点

### 6.1 画面与数据严格同步

**问题**：如果按"网页运行了多少秒"来推进数据，那么浏览器加载延迟、
视频卡顿、切后台、暂停、拖动进度都会让画面与数据脱节。

**方案**：唯一时间源是 `video.currentTime`，用 `requestAnimationFrame` 读取。

| 场景 | 结果 |
|---|---|
| 视频暂停 | `currentTime` 不变 → 数据自动冻结（**无需额外判断**） |
| 切换标签页 | rAF 暂停，恢复后重读真实值 → 不会因计时器累计而跑偏 |
| 拖动进度 | 下一帧立即同步到新位置 → 不会从旧状态慢慢增长 |
| 视频循环 | `currentTime` 变小 → 自动复位并开启新一轮趋势 |

**播放速率 0.5×**：源视频 10 s → 展示周期约 20 s。
只在浏览器侧调速，**不重新编码**，文件大小与源视频一致。
在 `loadedmetadata / loadeddata / canplay / play / playing / seeked`
**六个时机重复应用** —— 部分浏览器会在这些时点把它重置回 1.0。

**前后端两份实现 + 对等校验**：
后端 `app/services/video_sync.py` 是权威定义，前端
`src/video/videoTelemetry.ts` 是逐行等价实现（避免高频 HTTP 请求）。
用 `scripts/export_parity_fixtures.py` +
`frontend/scripts/check-telemetry-parity.mjs` 做**逐点比对**，
防止两边悄悄漂移。

### 6.2 视觉异常检测与证据链

**定位声明**：这是**展示层**的视觉异常表达，不是真实在线推理 ——
不运行 YOLO、不加载模型权重、不引入推理依赖。"有框"即代表"视觉已确认异常区域"。

**证据链闭环**：
```
摄像头画面 → 视觉模型检测 → 定位异常区域 → 生成带框证据图
→ 报警 → 供现场人员复核 → 处理结果进入数据溯源 → 经验进入知识库
```

**框位置如何确定**（方法论值得记录）：
物料带是灰棕色（实测 RGB≈111,90,86），与深色输送带对比度低，
**纯像素分割不可靠**（试过两轮阈值都误判了灰白设备）。
因此改用**人工目视 + ffmpeg 叠加候选框迭代**：先抽帧确认物料带走向，
再生成 8 个候选框逐一目视比对，最终选定一组坐标。

**证据图与网页的一致性保证**：
证据图由 `scripts/generate_evidence.py` 生成，坐标**从后端配置读取**
（单一事实源），不在脚本内重复写。因此网页上的框与图片上的框永远一致。

| 侧栏角标 | `status.today_warnings` | 今日发生的预警/严重报警**条数**（与是否处置无关） |

1. 角标改为与页面同口径（未处置记录数 + 临时报警数），为 0 时不显示
2. 「当前报警」补上**由画面实时派生的临时报警**，
   在内存中派生、**不写入任何存储**，画面回到正常阶段自然消失

## 10. 开发与部署流程

### 10.1 本机开发

```bash
# 后端（必须用 conda smoking 环境）
scripts\backend-daemon.bat          # Windows
```

**环境事实**：conda 环境 `smoking`（Python 3.12.14）；

### 10.2 部署流程（服务器不构建前端）

服务器 Node 为 v12 且无 npm，因此流程固定为「本地 build → 上传 dist」。

```bash
# 1. 上传
scp -r frontend/dist/* fengz:/tmp/smoking-dist/

# 2. 部署（保留 videos 目录）
ssh fengz "bash /tmp/update-dist.sh"

# 3. 后端源码变更时
scp -r backend/app/* fengz:/tmp/be-app/
ssh fengz "bash /tmp/deploy-be.sh"
```

### 10.3 替换视频素材的完整步骤

以主监控画面为例：

1. 视频命名为 `main-monitor.mp4`，复制到 `frontend/public/videos/`
2. **把 `MONITOR_VIDEO_VERSION` +1**（`MonitorVideo.tsx`）
3. 重新 `npm run build`
4. 上传 dist + 视频，执行部署
5. **重新生成证据图**：`python scripts/generate_evidence.py`

> 第 2 步和第 5 步是最容易漏的：不改版本号浏览器会继续放缓存里的旧视频
> （轮次 17 踩过）；不重做证据图会导致证据图与网页画面不一致（轮次 13 踩过）。

## 11. 全流程约束（必须遵守）

### 11.1 环境

- 必须使用 `conda activate smoking`

### 11.2 原始资料

  只有确实缺少原始口径时才回查

### 11.3 Git

- 仓库必须保持 **PRIVATE**，**不得创建新仓库**
- 每个主要里程碑提交并推送，不要攒成一个巨型提交
- **视频不入库**（`.gitignore` 用 `*.mp4` 通配规则），部署时单独上传

  `[System.IO.File]::WriteAllText($path, $msg, (New-Object System.Text.UTF8Encoding($false)))`
  + `git commit -F`，**不要用 `Out-File -Encoding utf8`**（会注入 BOM）

- 不引入不必要依赖；除 ECharts 外不引 UI / 图标 / 路由库

  （有测试断言防止误加）

### 11.5 数据与展示

- **不使用随机数**：所有演示数值由时间确定性推导，同一时刻结果一致
- **循环不写永久报警**：视频每约 20 秒循环一次，落库会让历史记录失去可信度
- **不用 `Date.now()` 驱动数据**：唯一时间源是 `video.currentTime`
- 界面文案纪律（见下）

### 11.6 界面文案纪律

这是项目过程中用户反复强调、并最终明确的三条原则：

1. **不写未实现的能力** —— 没有做的不要写出来，包括标注"规划中"的
2. **不写说明性质的文案** —— 功能做出来使用者自然看得懂，
   解释"我们怎么实现的"、"我们不会做什么"都属于多余
3. **不写开发视角的内容** —— 源码路径、开发约定、API 路径、
   启动命令等不应出现在界面上

**已清理的典型例子**：

## 12. 已知边界与未实现能力

这一节如实记录，避免对外表述时产生误解。

### 12.1 数据来源

平台当前的数据由内置监控服务统一提供，**不是从现场硬件实时采集的**。
但数据口径与设备规格完全一致（测距范围、精度、采集频率、基准距离、
报警阈值），接口结构已预留设备接入能力 ——
现场接入时替换数据源实现即可，业务与前端无需重写。

### 12.2 视觉检测

- 检测框是**展示层的异常区域标注**，不是实时在线推理
- 不运行 YOLO、不加载模型权重、不引入推理依赖
- 框位置由人工查看视频后标定，固定不变
- 模型能力通过**类别与置信度**体现

### 12.3 未实现（且界面中已不出现）

| 能力 | 状态 |
|---|---|
| 杂质检测与自动分拣（含机械臂联动） | **未实现** |
| LSTM 时序异常预测 | **未实现** |
| 多目标跟踪与场景理解 | **未实现** |
| 跨行业推广 | **未实现** |
| 企业微信 / 钉钉等消息推送 | **未接入**（平台内无此功能） |
| 真实设备直采 | **未接入**（接口已预留） |

### 12.4 演示机制的如实说明

- 主监控视频按 0.5× 播放，一个展示周期约 20 秒
- 画面中的物料堆积过程在真实系统中可能跨越更长时间
- 预测表达的是"在当前趋势持续条件下"的风险走向，
  **不是"多久之后一定堵料"的确定性结论**
